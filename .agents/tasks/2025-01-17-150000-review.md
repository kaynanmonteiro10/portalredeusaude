# Conferência de Adesões — Tela de Validação Automática

Implementação de uma tela portal para visualizar adesões estruturadas por lote, empresa, data, tipo (WEB/CRM) e status de conferência. Monaliza passa a ver tudo pronto em uma tabela com filtros por mês, ano e tipo, com botões para conferir em lote ou individualmente. A validação roda contra critérios locais (lote presente, empresa presente, data válida, vidas > 0) e marca cada adesão como conferida, alerta ou problema.

**Watch for**: 
- **[confirmed]** Schema mismatch: código tenta inserir/filtrar por coluna `data_adesao` que não existe na definição da tabela. 
- **[confirmed]** Botão Exportar Excel está ligado na UI mas sem implementação no JavaScript.
- **[likely]** Paginação não está implementada; limite de 500 registros pode ser insuficiente para volumes históricos.
- **[likely]** Validação corre apenas contra dados locais; nunca consulta o S4E ou base de empresas (o código menciona S4E mas valida offline).

**Verdict**: NEEDS_CHANGES

---

## High-level view

A tela é totalmente integrada ao índice existente como um painel ("adesiScreen") com seus próprios estilos CSS. A tabela carrega dados pelo GET `/api/adesoes` com filtros por mês, ano, tipo e busca por empresa/lote. A conferência individual ou em lote dispara POST `/api/adesoes/conferir-todos` ou `/api/adesoes/conferir/{id}`, que invoca o módulo local `adesoes_validation.py` para validar cada lote contra regras básicas (formato de data, quantidade de vidas > 0, campos não vazios). O resultado fica guardado como JSON na coluna `conferencia_resultado` da tabela. Linhas CRM e WEB têm cores de fundo diferentes (azul e verde). Badges mostram status: ✅ Conferido, ⚠️ Alerta, ❌ Problema, 🔵 Pendente — embora a lógica de alerta/problema seja incompleta porque a validação não diferencia entre erros e avisos no cálculo de KPI.

O problema crítico é que o schema SQL não contém a coluna `data_adesao` que o código tenta usar — isso causará erro em INSERT e SELECT. Além disso, o botão "Exportar Excel" não tem handler, deixando a funcionalidade visível mas morta. Paginação não existe; a lista pega sempre os 500 registros mais novos, o que pode deixar histórico antigo invisível.

### Database Schema Mismatch

O código backend referencia a coluna `data_adesao` em múltiplos endpoints sem que ela exista na schema. GET `/api/adesoes` ordena e filtra por essa coluna (linhas ~9485, 9505). POST `/api/adesoes` tenta inserir nela (linha ~11595). POST `/api/adesoes/conferir-todos` filtra por ela (linha ~11685). A schema.sql define apenas `data_entrada`, `criado_em` e `atualizado_em`, causando erro SQL "no such column" em qualquer operação.

A intenção aparenta ser distinguir data de entrada na empresa de data de adesão ao lote, mas a coluna nunca foi criada na tabela.

### Validação Offline, Não S4E

O módulo `adesoes_validation.py` valida apenas regras locais: lote/empresa não vazios, data não futura, data não > 1 ano atrás, vidas > 0 como número. Não consulta o S4E, não busca empresa em contratos reais, não compara dados contra parcelas efetivas. 

A função `validate_company_exists` existe mas retorna sempre `True`; nunca é chamada. A validação é puramente local (formato/range), não reconcilia contra dados reais — apropriado para detectar lotes incompletos mas não satisfaz "ver se a S4E devolve o que ela precisa" da requisição original.

### UI Não Diferencia Alertas de Erros

A validação retorna "errors" e "warnings" separados, mas o backend seta status como "validado" se há warnings-only, ou "erro" se há errors. Resultado: nenhuma row alcança "erro" com avisos; avisos silenciosos ficam invisíveis.

Frontend conta:
- `alertas = sum(1 for r in rows if r["conferencia_status"] == "erro")` — nunca alcança warnings-only
- `problemas = sum(1 for r in rows if r["conferencia_status"] == "erro")` — duplica lógica

KPI "Alertas" é sempre zero. UI mostra badge "⚠️ Alerta" mas nenhuma row o alcança. Decida: avisos devem ser status "validado com alerta" ou "validado" silencioso? Ajuste schema/backend/frontend coerentemente.

### Exportação Excel Não Implementada

Button `#adExportarBtn` existe no HTML mas sem event listener em `adesoes-conferencia.js`. ExcelJS 4.4.0 está carregado globalmente, pronto para uso. Handler precisa criar workbook, popular rows de `state.data.adesoes` com colunas (Lote, Empresa, Vidas, Valor, Data Entrada, Data Adesão, Tipo, Status, Situação, Conferido em, Observações), gerar .xlsx e disparar download.

### Paginação Ausente

Endpoint `/api/adesoes` tem `LIMIT 500` hardcoded. Histórico > 500 registros por período fica invisível; tabela não mostra "página X de Y". Para auditoria (Monaliza pode revisar adesões antigas), o corte silencioso é risco. Implemente paginação com offset/limit ou aumente limite com UI clara do que está sendo mostrado.

### Integração com Tela (Screen Navigation)

A tela está integrada corretamente ao `index.html` como `#adesiScreen`. Button de navegação usa `data-screen="adesiScreen"` e `access.js` chama `window.enterAdesiScreen()` / `window.leaveAdesiScreen()`. Estilos CSS usam variáveis de tema, suportam dark mode, e tabela diferencia CRM (azul) de WEB (verde) com cores de background.

Integração é limpa sem problemas estruturais.

### Data de Adesão Faltando

Monaliza precisa verificar quando a vida virou adesão (data efetiva) versus quando o lote entrou no sistema. Schema tem apenas `data_entrada`. O código tenta adicionar `data_adesao` mas a coluna não existe. Isso afeta a conferência: validação em `adesoes_validation.py` não inclui check de data de adesão.
